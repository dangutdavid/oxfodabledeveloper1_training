Part 2 · Week 2

Design & Build — Data model, Flows and Apex

This week you build: Cohort__c and Enrolment__c with relationships, roll-up, formulas and 2 validation rules · Contact.Total_Enrolments__c · 3 flows · the trigger, handler, Queueable and two invocable Apex services · sample data.

W2-A · The Week 2 prompt — have Claude generate it

In the same project folder, attach one document only: Oxfordable_Salesforce_Participant_Workbook_Week2.pdf. Then paste:

PROMPT — WEEK 2 
Read the attached Week 2 workbook. Extend my existing careerlaunch SFDX project with the
full Lab 2-4 build, exactly matching the workbook's solution design (British spelling
Enrolment__c with one "l" everywhere):

DATA MODEL (Lab 2)
1. Cohort__c - Record Name Auto Number CO-{0000}; fields: Course__c (required Lookup to
   Course__c), Start_Date__c (Date, required), End_Date__c (Date), Delivery_Mode__c
   (Picklist: Online, In-Person, Hybrid), Capacity__c (Number(3,0), required, default 20),
   Status__c (Picklist: Planned, Open, Full, Running, Completed, Cancelled),
   Enrolled_Count__c (Roll-Up Summary: COUNT of Enrolments where Status not equal to
   Cancelled), Seats_Remaining__c (Number formula: Capacity__c - Enrolled_Count__c),
   Cohort_Label__c (Text formula: Course__r.Name & " - " & TEXT(Start_Date__c)).
   Validation rule End_Date_After_Start_Date:
   AND(NOT(ISBLANK(End_Date__c)), End_Date__c < Start_Date__c)
   with error "End Date cannot be earlier than Start Date."
2. Enrolment__c - Record Name Auto Number ENR-{00000}; fields: Cohort__c (Master-Detail
   to Cohort__c), Student__c (required Lookup to Contact), Status__c (Picklist: Applied
   default, Confirmed, Waitlisted, Cancelled, Completed), Enrolment_Date__c (Date),
   Amount_Paid__c (Currency(10,2), default 0), Enrolment_Key__c (Text 64, External ID,
   Unique), Attendance_Percent__c (Percent(3,0)), Certificate_Issued__c (Checkbox).
   Validation rule Payment_Not_Above_Fee: Amount_Paid__c > Cohort__r.Course__r.Fee__c
   with error "Amount Paid cannot exceed the course fee."
3. Contact.Total_Enrolments__c Number(3,0). Custom tabs for Cohort and Enrolment.

FLOWS (Lab 3)
4. Enrolment_Confirmed_Actions - record-triggered after-save on Enrolment__c, created or
   updated, entry condition Status__c = Confirmed only when updated to meet it. Elements:
   Get the parent Cohort; Send Email to {!$Record.Student__r.Email} with subject
   "Your place is confirmed - {!$Record.Cohort__r.Cohort_Label__c}" and a welcome body
   (put a FAULT PATH on the email action so a failed email never blocks the save);
   Create a Task "Send welcome pack to {!$Record.Student__r.Name}" owned by the Cohort's
   owner, due today, priority High; Decision: Seats_Remaining <= 0; on Yes update the
   Cohort Status to Full. Deploy it Active.
5. Quick_Enrol_Student - screen flow: course picklist (record choice set on active
   Courses) -> cohort radio buttons (record choice set on Open cohorts of that course,
   labelled by Cohort_Label__c) -> student Lookup component (Enrolment__c.Student__c) ->
   Get the selected Course -> Apex action "Find Available Cohorts" -> decision on
   seatsAvailable -> create the Enrolment as Confirmed -> success screen; a "cohort just
   filled up" screen on No; fault connectors from every Get/Create/Action element to an
   error screen showing {!$Flow.FaultMessage}. Deploy it Active.
6. Cohort_Start_Reminder - schedule-triggered daily at 07:00: get Confirmed enrolments,
   loop with a decision Cohort__r.Start_Date__c = {!$Flow.CurrentDate}+3 (Date formula),
   build reminder Tasks into a collection, one Create Records after the loop (no DML in
   the loop). Deploy it Active.

APEX (Lab 4) - bulk-safe, no SOQL or DML inside loops, human-readable errors
7. EnrolmentTrigger (before insert/update, after insert/update) routing only, plus
   EnrolmentTriggerHandler with methods: setDefaults (Enrolment_Date today, Status
   Applied, Amount_Paid 0), buildUniqueKey (Enrolment_Key__c = first 15 chars of
   CohortId + "-" + first 15 of StudentId), preventOverbooking (count newly-consuming
   seats per cohort, ONE query for the cohorts, allocate seats in memory, addError
   "This cohort is full. Please choose another cohort or add the student to the waiting
   list." on records over capacity), enqueueStudentSummary (enqueue the Queueable,
   respecting the queueable job limit).
8. StudentSummaryQueueable - aggregate non-cancelled enrolments per student with one
   GROUP BY query and write Contact.Total_Enrolments__c (zero everyone first so
   cancellations are reflected).
9. CohortAvailabilityService - @InvocableMethod "Find Available Cohorts": input
   courseName; query Open future cohorts whose Course name matches LIKE; keep those with
   Seats_Remaining > 0; outputs: answer (human-readable summary), cohorts (list),
   seatsAvailable (boolean). Write a clear description on every @InvocableVariable.
10. EnrolmentStatusService - @InvocableMethod "Check Enrolment Status": input
    studentEmail; return the student's enrolments (cohort label, start date, status) as
    an answer string plus a found boolean.

Also write scripts/apex/seed.apex creating: cohort CO-0001 (Introductory course, starts
today+14, capacity 3, Open), CO-0002 (Advanced, today+30, capacity 10, Open), and 3
student Contacts with email addresses.

Deploy everything to <your-org-username>, run the seed script, then commit with message
"Week 2: data model, flows, Apex" and push to
https://github.com/<your-github-username>/<your-repo-name>.

W2-B · Or build it by hand (click path)

  2. Fields in this order: Cohort — Master-Detail → Cohort (first!) · Student (Lookup → Contact, required) · Status (Picklist, Applied default, Confirmed, Waitlisted, Cancelled, Completed) · Enrolment Date (Date) · Amount Paid (Currency 10,2, default 0) · Enrolment Key (Text 64, tick External ID + Unique) · Attendance % (Percent 3,0) · Certificate Issued (Checkbox).

  • Tidy the Cohort page layout (add the 3 calculated fields + the Enrolments related list); create the sample data by hand or with the seed script.

W3-A · The Week 3 prompt — have Claude generate it

Attach one document only: Oxfordable_Salesforce_Participant_Workbook_Week3.pdf. Then paste:

PROMPT — WEEK 3 
Read the attached Week 3 workbook. Finish my careerlaunch SFDX project with Labs 5-8:

LWC + CONTROLLERS (Lab 5)
1. CohortController - @AuraEnabled(cacheable=true) getActiveCourses() and
   getOpenCohorts(Id courseId): Open, future-dated cohorts, optionally filtered by
   course, WITH SECURITY_ENFORCED, ordered by Start Date.
2. EnrolmentController - @AuraEnabled createEnrolment(cohortId, studentId, status):
   insert as Confirmed inside try/catch; on DmlException rethrow AuraHandledException
   with a friendly sentence (translate "duplicate value found" into "That student is
   already enrolled on this cohort."); return the saved record with its Name.
3. LWC cohortExplorer - course combobox + lightning-datatable of open cohorts (Cohort,
   Course, Starts, Mode, Capacity, Seats left) via @wire; row selection dispatches a
   "cohortselected" CustomEvent; public @api refresh() using refreshApex.
4. LWC enrolmentPanel - receives the cohort via @api; lightning-record-picker for the
   Contact; imperative call to createEnrolment; success toast; "enrolled" event up;
   NavigationMixin to the new record; error toast with the friendly message.
5. LWC enrolmentConsole - wrapper wiring the two together (data down via
   cohort={selectedCohort}, events up calling explorer.refresh()), exposed to
   lightning__AppPage.
6. A FlexiPage app page named "Enrolment_Console" containing enrolmentConsole.

TESTS (Lab 7) - all data created in-test, no hard-coded IDs, meaningful asserts
7. TestDataFactory - createCourse, createCohort, createStudents (insert Contacts with
   Database.DMLOptions DuplicateRuleHeader.allowSave = true so org duplicate rules never
   break tests), buildEnrolments (returned NOT inserted - the caller decides).
8. EnrolmentTriggerTest - testDefaultsApplied; testOverbookingBlocked (negative test
   with Database.insert(record, false)); testBulkInsertRespectsCapacity (200 records
   loaded as Applied against capacity 150 - assert the cohort NEVER exceeds capacity
   and the 50 overflow records are blocked); testDuplicateEnrolmentBlocked;
   testQueueableUpdatesContact (Test.startTest/stopTest forces the async job).
9. CohortServicesTest - both controllers and both invocable services, happy and error
   paths.

SECURITY + RELEASE (Lab 8)
10. Permission set Enrolment_Console_User: Read/Create/Edit on Course__c, Cohort__c and
    Enrolment__c; Read on Contact; field permissions on all custom fields (formulas and

    the Quick_Enrol_Student flow; the three tabs Visible.
11. manifest/package.xml covering everything built across all three weeks.

W3-B · Manual steps you must finish in the org (click path)

Activate the Enrolment Console page (US-10)

  1. Setup → Lightning App Builder → open Enrolment Console → Activation… → Lightning Experience tab → add to an app (e.g. Sales) → Save.
  2. App Launcher → Enrolment Console → filter by course, select a cohort, pick a student, Enrol student → a toast appears, the seat count drops, and an overbooking attempt is still blocked by the Week 2 trigger.

Build the Agentforce agent (US-11, US-12) — Setup only, not deployable by CLI

  1. Setup → Einstein Setup → turn on → Setup → Agentforce Agents (assign yourself the Agentforce permission set if prompted).
  2. New Agent: type Employee/internal · Name Oxfordable Student Assistant · Role “Answers questions about our courses, cohort availability and a student's own enrolment status.” · Company “Oxfordable Careers, a technology training provider.” · Tone: warm, concise, professional — never invent dates, prices or seat numbers.
  3. Two actions from your invocable Apex: Find Available Cohorts (input Course Name) and Check Enrolment Status (input Student Email). Write every input/output description for a colleague who has never seen your org — thin descriptions are the number-one reason agents misbehave.
  4. Topic “Course Enrolment Enquiries” — classification: “Use this topic when someone asks about our courses, when a cohort starts, whether seats are available, how to join, or the status of an enrolment they already hold.” Scope: answer only from the assigned actions. Instructions: confirm the course before searching · always state start date and seats remaining · offer the waiting list when full · ask for the booking email for status questions · never share one student's details with another · pass anything else to the team. Assign both actions.
  5. Test in the preview: “Do you have any Advanced cohorts with space?” → live list · “What is the status of my enrolment?” → asks for the email · an off-topic question → graceful decline. Read the reasoning trace after each test. Then Activate.

Appendix A · Fixes discovered in the reference deployment (expect these)

SymptomRoot causeFix
Contact inserts fail in tests with DUPLICATES_DETECTEDThe org has an active Contact duplicate ruleTestDataFactory inserts contacts with Database.DMLOptions.DuplicateRuleHeader.allowSave = true
QueryException “secure query included inaccessible field”WITH SECURITY_ENFORCED enforces the running user’s FLS; API-created fields grant FLS to nobodyAssign the Enrolment_Console_User permission set before running tests
CANNOT_EXECUTE_FLOW_TRIGGER on confirmed enrolments in testsThe flow’s Send Email action failed (deliverability/limits) and killed the saveFault path on the email action so a failed email never blocks the enrolment
Bulk test expected exactly 150 successes, got fewerPartial-save retries + the unique key make “exactly capacity” non-deterministic in one 200-record batchAssert the true invariant: the cohort can never exceed capacity, and the overflow records are always blocked
