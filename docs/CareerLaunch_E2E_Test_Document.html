1Introduction & test approach

What this document is for, what it covers, and the rules for executing it.

1.1 Purpose

This document proves, end to end and against written acceptance criteria, that the CareerLaunch platform behaves as specified — the core enrolment engine (user stories US-01…US-14) and the Extension Pack features (invoicing, payments, certificates, currency & language, error logging, and the Experience Cloud student portal). It is written so that a tester who has never seen the org can execute every case unaided.

1.2 References

DocumentUsed for
Week 2 Participant Workbook v2.0 — Section 1User stories US-01…US-13 and their acceptance criteria; NFR-01…06
Week 3 Participant Workbook — “The three stories we deliver today”US-10…US-12, US-14 acceptance criteria
CareerLaunch Complete Build GuideExtension feature behaviour (Chapters 7–12) and release procedure (Chapter 14)
User Guide / Technical GuideExpected day-to-day behaviour and architecture reference

1.3 Scope

In scopeOut of scope
All functional acceptance criteria of the core system and Extension Pack, tested through the real UI, real flows, real Apex and the real (stubbed) gateway in a Developer/QA orgPerformance/load testing beyond the 200-record bulk case · penetration testing · real payment-provider integration (the gateway runs the deterministic stub) · email deliverability beyond the org's own send

1.4 Entry criteria

  • The full application is deployed to the test org and all unit tests pass (verified formally again in E2E-45).
  • Both permission sets exist and are assigned per Section 2.2.
  • Email deliverability is All Email; all flows are Active; the Experience Cloud site is published.
  • The seed data of Section 2.3 has been created exactly as written.

1.5 Exit criteria

  • 100% of applicable cases executed; every Must-priority case passed; no open Critical or High defect.
  • Suite E (agent) may be marked N/A if Agentforce is unavailable in the org — record N/A, not Fail.
  • The traceability matrix (Section 15) shows every acceptance criterion covered by at least one passed case.

1.6 Defect recording

Raise every failure with: the test case ID, the step number that failed, expected vs actual, a screenshot, and — where the failure produced one — the Error Log number (ERR-xxxxx from the Error Logs tab), which carries the stack trace the developer needs. Severity scale: Critical (money wrong, data loss, security breach) · High (acceptance criterion fails) · Medium (workaround exists) · Low (cosmetic).

1.7 How to execute a case

  • Run cases in order within a suite — later cases reuse earlier state (e.g. G-suite pays the invoice F-suite created).
  • Perform every step exactly; do not substitute data. Where a step says “as Staff Tester”, log in as that user (Section 2.2).
  • Tick each expected result individually. A case passes only when all its expected results hold.
  • Record Pass / Fail / N/A, tester initials and date in the result strip of each case.
Reset rule
If you must re-run a suite, create fresh records rather than editing used ones — auto-numbers and error logs are audit evidence. Never delete Error Log records during the test cycle.
