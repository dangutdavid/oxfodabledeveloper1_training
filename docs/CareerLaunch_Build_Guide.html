1The business problem & the solution

Every build starts with a client, not a click. Read this chapter before touching Setup — everything you create later traces back to a sentence here.

1.1 The client brief — "Oxfordable CareerLaunch"

Client: Oxfordable Careers

Oxfordable Careers runs a growing catalogue of technology training courses. Each course runs several times a year as a cohort with a fixed start date, a delivery mode and a limited number of seats. Today the team tracks everything in spreadsheets and WhatsApp: students get double-booked, cohorts get oversold, welcome emails are forgotten, invoices are typed by hand, certificates are made in a word processor, and nobody can answer "how many seats are left?" without opening three files.

They want one Salesforce application that manages courses, cohorts and enrolments; stops overselling; automates welcome and reminders; raises and takes payment for invoices; issues completion certificates as PDFs; gives students a self-service portal in their own language and currency; records every error somewhere staff can see; and gives the admissions team a one-screen console.

The layering principle
The portal, the console and any future AI agent are only channels. They all call the same Apex service layer, over the same data model, protected by the same trigger. Build the core once; expose it many times.

1.4 How code works in this guide

You build every object, field, tab, flow, label, setting and permission with clicks — those steps are written out in full. For Apex classes, triggers, the Visualforce page and Lightning Web Components, this guide names the file and a Code Pack item, like this: CODE PACK 10.4. Ask your instructor for that item (or open the matching file in the project repository — Appendix A maps every item to its file), type or paste it exactly, and read the comments — they explain why the code is shaped the way it is.

Build in chapter order
Later code calls earlier code (for example, the payment client calls the error logger). Follow the chapters in order and nothing will ever fail to compile. Do not skip checkpoints — they are how you catch a problem while it is still one step old.

The code half of the automation matrix: things clicks genuinely cannot do — counting sibling records in bulk, database-enforced duplicate prevention, asynchronous aggregation, and services that Flow (and later a portal) can call.

5.1 Which tool, and why — the decision matrix

RequirementTool chosenWhy not the alternative
Seat count on a cohortRoll-up + formulaNo automation needed at all — always ask "can a field do this?" first
Welcome email + taskRecord-triggered flowDeclarative, no test class, admin-editable. Apex would be over-engineering

7Error logging framework

One front door for every error — flows, triggers, Apex, integrations — that survives transaction rollback. Built now because Chapters 10 and 11 call it.

7.1 The idea

Why an event, not an insert
If a failing transaction rolls back, a plain insert Error_Log__c rolls back with it — the error erases its own evidence. So the code publishes a publish-immediately platform event (which escapes the rollback); a trigger on the event then writes the permanent record in a fresh transaction, as the Automated Process user.
code / flow fault ─► ErrorLogger ─► Error_Log_Event__e (publish immediately)
                                        └─► ErrorLogEventTrigger ─► Error_Log__c (+ tab)

Why two amounts and a frozen rate
Amount__c is always GBP, the org's one true currency. The rate is stamped onto the invoice at issue time and the display amount is a formula over the two — so an admin editing tomorrow's rates can never change what an already-issued invoice is worth.

10Payment gateway & automatic invoicing

The full payment stack: an interface, a metadata-driven factory, a deterministic stub for this org, a production-ready HTTP client, and the services that raise and settle invoices. The most interview-valuable chapter in the guide.

The seam principle — say it out loud
Everything above the interface knows nothing about HTTP; everything below it knows nothing about enrolments. Swapping the stub for a real provider is a custom-metadata edit, not a code change. This is how real teams stub an external system they cannot reach from a training org.

10.1The Named Credential

Setup → Quick Find Named Credentials → dropdown next to New → New Legacy.
Label Payment Gateway · Name Payment_Gateway · URL https://api.payments.example.com · Identity Type Anonymous · Protocol No Authentication → Save.

The credential owns the URL and (in production) the secrets, so Apex never contains either. The URL is a placeholder — nothing calls it while the stub is configured.

10.2Build the eight pieces, in order

11Certificate PDF generation

A designed A4 certificate rendered as a real PDF, stored as a File on the enrolment, triggered by a flow when the student completes.

The pattern in one paragraph
A Visualforce page with renderAs="pdf" is the platform's built-in PDF engine. Turning the page into a stored file uses getContent(), which counts as a callout and is banned in triggers — so the render happens asynchronously, in a Queueable that declares Database.AllowsCallouts. Failures are logged via Chapter 7 (async work has no user watching).

Replace the markup with 11.2. Find in it: renderAs="pdf", the A4-landscape @page CSS, and the four {!$Label.Certificate_…} merge fields — a French student receives a French certificate.
See it now: browse to https://<your-domain>/apex/CertificatePdf?id=<enrolment id> (copy the 18-character id from any Enrolment URL) — a PDF renders in the browser.
Create class CertificateService — 11.3. Find: the @InvocableMethod Issue Completion Certificate; the inner IssueJob queueable; the Certificate_Issued__c = false filter (never issued twice); ContentVersion with FirstPublishLocationId (files and links the PDF in one insert); try/catch → ErrorLogger; and the Test.isRunningTest() guard (getContent() is blocked in unit tests).

12The Experience Cloud student portal

A public-facing site where each student sees only their own records, pays with one click, and downloads their certificate. Read the security model first — it is the design decision of the chapter.

The security model — three rules, all server-side
1. Every query starts from the logged-in user's Contact — the browser never says whose data to load. 2. payInvoice re-checks ownership on the server before money moves. 3. The controller is without sharing, deliberately: Enrolment__c is a master-detail child (sharing controlled by its parent Cohort, which has no contact field), so Experience Cloud sharing sets cannot reach it. Row-level privacy lives in the contact-scoped WHERE clauses instead — and there is a test that proves it in Chapter 14.

13.3 The portal privacy model — summary

  • Sharing sets cannot target Enrolment (master-detail child of Cohort; Cohort has no contact field). Row privacy is enforced in Apex: contact-scoped queries + the payInvoice ownership check.
